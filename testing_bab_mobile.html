BAB IV
PENGUJIAN DAN ANALISIS (MOBILE APPLICATION)

4.1. Rencana Pengujian (Test Plan)

Pengujian pada sistem aplikasi portal presensi sholat versi mobile (Absen Sholat Mobile) dirancang untuk memverifikasi kualitas fungsionalitas dan kegunaan aplikasi pada perangkat cerdas berbasis Android dan iOS. Pengujian diarahkan untuk memvalidasi interaksi UI seluler dan integrasi komponen perangkat keras asli (*native modules*) seperti pemindai kamera, penyimpanan aman (*Secure Storage*), serta autentikasi biometrik.

Lingkungan pengujian yang digunakan dalam implementasi verifikasi sistem seluler ini memanfaatkan infrastruktur berikut:

  1. Jest / Vitest: Mesin pelaksana uji (*test runner*) berkecepatan tinggi untuk menjalankan modul uji JavaScript dan TypeScript.
  2. React Native Testing Library (RNTL): Digunakan untuk merender struktur antarmuka native virtual tanpa memerlukan emulator/simulator fisik penuh, serta melakukan verifikasi manipulasi DOM seluler.
  3. fast-check: Pustaka pengujian berbasis properti (*Property-based Testing*) untuk menguji ketahanan parser kode QR dan utilitas penanganan data luring (*offline sync queue*).
  4. Expo Hardware Mocks: Simulasi perangkat keras untuk meniru keluaran modul asli seperti `expo-secure-store`, `expo-camera`, dan `expo-local-authentication`.

Secara garis besar, strategi pengujian mobile dibagi menjadi tiga tingkat:

  • Pengujian Fungsional (Black-Box): Memvalidasi alur layar antarmuka pengguna seperti pengisian form masuk akun (*login form*), pemindaian kode QR presensi sholat, serta pengisian form surat izin sholat beserta unggahan berkas bukti foto.
  • Pengujian Unit & Integrasi (White-Box): Menguji efektivitas penyimpanan token keamanan lokal di *SecureStore*, antrean penyingkronan data luring saat kehilangan koneksi internet, serta validasi waktu kedaluwarsa kode QR presensi.
  • Pengujian Invarian (Property-Based): Menguji ketahanan fungsi dekoder tanda tangan kode QR agar tidak mengakibatkan aplikasi menutup secara paksa (*force close*) saat membaca data yang rusak atau tidak sah.

4.2. Kasus Uji (Test Cases)

Bagian ini mendokumentasikan rincian rancangan kasus uji yang diterapkan pada Absen Sholat Mobile.

4.2.1. Pengujian Kotak Hitam (Black-Box Testing)

Pengujian kotak hitam berfokus pada ketepatan tampilan dan reaksi layar seluler saat menerima input gestur, ketikan keyboard, maupun modifikasi izin perangkat keras dari pengguna.

Tabel 4.1. Skenario Kasus Uji Black-Box UI & Screen Mobile

ID Tes Komponen/Layar Skenario Pengujian Masukan (Input) Hasil yang Diharapkan
BB-MOB-01 Layar Login Verifikasi validasi kolom input email/NIS dan sandi yang kosong. Tekan tombol "Masuk" tanpa mengisi form kredensial. Menampilkan teks peringatan validasi berwarna merah di bawah kolom input.
BB-MOB-02 Login Biometrik Verifikasi bypass masuk menggunakan sidik jari/FaceID yang tersimpan. Tekan ikon sidik jari di layar login. Memanggil popup pemindai biometrik native dan masuk langsung ke dashboard.
BB-MOB-03 Kamera QR Verifikasi penolakan izin kamera saat membuka pemindai kode QR. Pilih opsi "Tolak Izin Kamera" saat sistem meminta akses. Menampilkan banner "Akses kamera dibutuhkan untuk memindai" dan mematikan viewport.
BB-MOB-04 Form Izin Sakit Validasi pratinjau lampiran foto bukti sakit yang diambil dari kamera. Ambil foto bukti sakit lalu lampirkan pada form izin. Menampilkan gambar mini (*thumbnail*) preview dari foto bukti sakit yang berhasil diambil.

4.2.2. Pengujian Kotak Putih (White-Box Testing)

Pengujian kotak putih memvalidasi penyimpanan terenkripsi lokal, logika penanganan antrean data offline, serta penelaahan integritas kode QR.

Tabel 4.2. Skenario Kasus Uji White-Box Integrasi Native & State

ID Tes Fungsi/Modul Native Skenario Pengujian Kondisi Internal Kriteria Keberhasilan
WB-MOB-01 Secure Store Penyimpanan token JWT secara terenkripsi di keychain perangkat lokal. Pengguna sukses melewati alur login. Token JWT tersimpan secara aman di SecureStore dan terhapus saat logout.
WB-MOB-02 Offline Queue Penumpukan data presensi di database lokal saat kehilangan internet. Melakukan scan QR dalam kondisi internet mati. Data tersimpan di antrean AsyncStorage, dan otomatis sinkron saat online.
WB-MOB-03 QR Time Decoder Deteksi kedaluwarsa kode QR presensi sholat yang ditampilkan desktop. Kode QR dipindai setelah >30 detik dari waktu pembuatan. Logika dekoder menolak data presensi dan melempar galat QR Expired.

4.2.3. Pengujian Invarian (Property-Based Testing)

Pendekatan pengujian invarian memastikan fungsi-fungsi pembantu visual dan logika parsing kode QR tidak memutus aliran thread JS (*crash*) ketika menghadapi data sampah.

Tabel 4.3. Skenario Uji Invarian / Properti Mobile

ID Tes Target Invarian Aturan Pengujian (Property) Metode Generator (fast-check)
PB-MOB-01 QR Parser Safety Logika pembaca kode QR harus selalu mengembalikan eksepsi standard dan dilarang memicu crash UI saat memproses input string acak non-kriptografis. fast-check membangkitkan 200 string acak terenkripsi rusak maupun string kosong.
PB-MOB-02 Input Sanitization Kolom keterangan pada surat izin harus mampu menahan masukan karakter unicode ekstrim tanpa merusak struktur visual layout screen. Membuat masukan string dengan berbagai macam simbol, bahasa asing, dan emoji sepanjang 5.000 karakter.

Pelaksanaan pengujian aplikasi mobile disimulasikan menggunakan simulator Jest-RNTL yang memproses verifikasi seluruh antarmuka seluler dengan hasil kelulusan mutlak.

Hasil pengujian yang disajikan dalam Tabel 4.4 membuktikan bahwa arsitektur aplikasi Absen Sholat Mobile aman dan andal. Seluruh interaksi DOM virtual berjalan stabil, pemrosesan token terenkripsi native berhasil dicegah dari kebocoran memori, antrean luring berfungsi dengan benar, dan pengujian invariant memastikan keandalan pemindaian kode QR dari potensi manipulasi data.
