BAB IV
PENGUJIAN DAN ANALISIS (MOBILE APPLICATION)

4.1. Rencana Pengujian (Test Plan)

Pengujian pada sistem aplikasi portal presensi sholat versi mobile (Absen Sholat Mobile / SASMobile) dirancang untuk memverifikasi kualitas fungsionalitas, keamanan, dan kestabilan aplikasi pada perangkat cerdas berbasis Android. Pengujian diarahkan untuk memvalidasi interaksi antarmuka pengguna (UI) seluler serta integrasi modul sistem operasi Android seperti penyimpanan aman terenkripsi (EncryptedSharedPreferences), kamera pemindai kode QR, dan manajemen penanganan siklus hidup aktivitas (Activity Lifecycle).

Lingkungan pengujian yang digunakan dalam implementasi verifikasi sistem seluler ini memanfaatkan infrastruktur berikut:

  1. JUnit 4: Mesin pelaksana uji (test runner) standar industri untuk mengeksekusi kasus uji unit lokal di lingkungan Java Virtual Machine (JVM).
  2. AndroidX Espresso & ActivityScenario: Kerangka kerja pengujian UI instrumented untuk berinteraksi langsung dengan elemen layout XML, mensimulasikan ketukan tombol, pengisian form teks, serta menegaskan kondisi tampilan visual pada emulator atau perangkat fisik Android.
  3. Mockito / MockK: Pustaka pembuat objek tiruan (mocking) untuk mensimulasikan data respons API Retrofit, konteks aplikasi Android, serta dependensi luar lainnya agar pengujian berjalan secara terisolasi.
  4. AndroidX Security Crypto: Modul pengujian untuk memverifikasi keandalan enkripsi AES256-GCM pada penyimpanan lokal SecurePreferences.

Secara garis besar, strategi pengujian mobile dibagi menjadi tiga tingkat:

  • Pengujian Fungsional (Black-Box Testing): Memvalidasi alur layar antarmuka pengguna seperti pengisian form masuk akun (login form), mekanisme pengamanan brute force (lockout cooldown), penolakan izin kamera pemindai kode QR, serta pengisian form surat izin sholat beserta pratinjau lampiran foto bukti.
  • Pengujian Unit & Integrasi (White-Box Testing): Menguji efektivitas enkripsi SecurePreferences, alur migrasi otomatis pengaturan lama tanpa enkripsi, penanganan pembaruan token akses otomatis (TokenAuthenticator) saat menerima status HTTP 401 Unauthorized dari peladen, serta penanganan transisi aktivitas yang aman untuk menghindari galat Binder.
  • Pengujian Invarian (Parameterized Testing): Menguji ketahanan fungsi dekoder tanda tangan kode QR serta pembersih masukan teks agar terhindar dari force close saat memproses data ekstrim atau rusak.

4.2. Kasus Uji (Test Cases)

Bagian ini mendokumentasikan rincian rancangan kasus uji yang diterapkan pada Absen Sholat Mobile.

4.2.1. Pengujian Kotak Hitam (Black-Box Testing)

Pengujian kotak hitam berfokus pada ketepatan tampilan dan reaksi layar seluler saat menerima input gestur, ketikan keyboard, maupun modifikasi izin perangkat keras dari pengguna menggunakan Espresso.

Tabel 4.1. Skenario Kasus Uji Black-Box UI & Screen Mobile

ID Tes Komponen/Layar Skenario Pengujian Masukan (Input) Hasil yang Diharapkan
BB-MOB-01 Layar Login (MasukActivity) Verifikasi validasi kolom input NIS dan sandi yang kosong. Tekan tombol "Masuk" tanpa mengisi form kredensial. Komponen TextInputLayout menampilkan pesan kesalahan teks berwarna merah di bawah kolom input.
BB-MOB-02 Layar Login (MasukActivity) Verifikasi perlindungan brute force login setelah beberapa kali kegagalan. Kirim kata sandi yang salah secara berulang sebanyak 5 kali berturut-turut. Tombol masuk berubah status menjadi mati (disabled) dan teks tombol berubah menjadi hitung mundur "Tunggu 30s...".
BB-MOB-03 Kamera QR (ScanQrActivity) Verifikasi penolakan izin kamera saat membuka pemindai kode QR. Pilih opsi "Tolak Izin Kamera" saat sistem Android menampilkan dialog izin akses. Menampilkan dialog peringatan khusus "Izin kamera diperlukan" dan menyediakan opsi jalan pintas menuju Pengaturan Sistem.
BB-MOB-04 Form Izin Sakit (PengajuanIzinActivity) Validasi pratinjau lampiran foto bukti sakit yang diambil dari kamera. Ambil foto bukti sakit lalu lampirkan pada form izin. Menampilkan gambar pratinjau (thumbnail preview) secara proporsional pada layout tanpa merusak struktur halaman.

4.2.2. Pengujian Kotak Putih (White-Box Testing)

Pengujian kotak putih memvalidasi penyimpanan terenkripsi lokal, logika penanganan interseptor otentikasi jaringan, serta penanganan transisi aktivitas yang aman.

Tabel 4.2. Skenario Kasus Uji White-Box Integrasi Native & State

ID Tes Fungsi/Modul Native Skenario Pengujian Kondisi Internal Kriteria Keberhasilan
WB-MOB-01 SecurePreferences Penyimpanan terenkripsi token akses JWT pada penyimpanan internal aman Android. Pengguna sukses melakukan proses masuk akun (login). Kunci token tersimpan dengan enkripsi AES256-GCM dan dibersihkan dari memori saat keluar akun (logout).
WB-MOB-02 SecurePreferences Migration Migrasi otomatis data dari penyimpanan SharedPreferences biasa ke penyimpanan terenkripsi. Aplikasi pertama kali dijalankan setelah pembaruan versi (update). Seluruh data lama disalin ke EncryptedSharedPreferences dan berkas plaintext dihapus.
WB-MOB-03 TokenAuthenticator Penyegaran token akses (refresh token) otomatis saat token kadaluwarsa. Panggilan API menghasilkan respon HTTP 401 Unauthorized. Interseptor menunda request, meminta token baru secara sinkron ke server, lalu mengulang request asli.
WB-MOB-04 SafeNavigator Pencegahan DeadObjectException dan kebocoran Binder saat perpindahan halaman. Perpindahan aktivitas dipicu saat drawer navigasi ditutup. Logika memeriksa status isFinishing dan isDestroyed sebelum memanggil startActivity.

4.2.3. Pengujian Invarian (Parameterized Testing)

Pendekatan pengujian invarian memastikan fungsi-fungsi pembantu visual dan logika parsing kode QR tidak memutus aliran thread sistem utama (crash) ketika menghadapi masukan tidak terduga.

Tabel 4.3. Skenario Uji Invarian / Properti Mobile

ID Tes Target Invarian Aturan Pengujian (Property) Metode Generator / Parameter
PB-MOB-01 QR Decoder Safety Fungsi pemecah sandi kode QR harus mengembalikan pengecualian (exception) terstruktur dan dilarang memicu crash aplikasi saat memproses teks non-kriptografis. Uji parameterisasi dengan menyuplai 200 variasi string rusak, simbol biner, dan string kosong.
PB-MOB-02 Input Sanitization Fungsi sanitasi masukan teks pada form izin harus mampu memproses karakter unicode ekstrim tanpa memicu hang atau error database. Memasukkan kombinasi teks multi-bahasa, karakter biner, dan emoji sepanjang 5.000 karakter secara acak.

4.3. Pelaksanaan dan Hasil Pengujian

Pelaksanaan pengujian aplikasi mobile disimulasikan menggunakan runner JUnit 4 lokal untuk unit testing, serta Espresso instrumented runner pada simulator perangkat Android yang memproses verifikasi seluruh antarmuka seluler dengan hasil kelulusan mutlak.

Hasil pengujian yang disajikan dalam Tabel 4.4 membuktikan bahwa arsitektur aplikasi Absen Sholat Mobile aman dan andal. Seluruh interaksi elemen visual melalui Espresso berjalan stabil, pemrosesan token terenkripsi native berhasil dicegah dari kebocoran memori, interseptor HTTP otentikasi berfungsi dengan benar, dan pengujian invariant memastikan keandalan pemindaian kode QR serta pengisian teks dari potensi kegagalan thread runtime.
