BAB IV
PENGUJIAN DAN ANALISIS (API BACKEND)

4.1. Rencana Pengujian (Test Plan)

Pengujian pada sistem antarmuka pemrograman aplikasi (API Backend) presensi sholat terpadu (Absen Sholat API) dirancang untuk memverifikasi keamanan, stabilitas, dan ketepatan pemrosesan data di sisi peladen (server). Pengujian sistem ini memvalidasi keandalan logika rute internal serta ketahanan API terhadap masukan yang salah atau berbahaya.

Lingkungan pengujian yang digunakan dalam implementasi verifikasi sistem API ini memanfaatkan infrastruktur berikut:

  1. Go Testing Toolchain: Kerangka kerja pengujian bawaan (*native test runner*) bahasa pemrograman Go untuk mengeksekusi suite pengujian secara paralel.
  2. Testify (assert/require): Pustaka pembantu untuk menyatakan ekspektasi kondisi keluaran (*assertion*) dengan sintaksis yang jelas dan ekspresif.
  3. SQLite In-Memory Driver: Digunakan sebagai tiruan database (*mock database*) sementara yang diisolasi di memori RAM selama pengujian berlangsung, menghindari modifikasi pada database PostgreSQL utama.
  4. httptest (net/http/httptest): Emulator panggilan HTTP untuk mensimulasikan permintaan klien (*request*) dan merekam respons peladen (*response recorder*) tanpa melakukan pengikatan port fisik TCP.
  5. Go Fuzzing Engine: Metode pengujian berbasis input acak otomatis bawaan Go (*fuzz testing*) untuk menguji fungsi utilitas seperti penelaah token JWT (*JWT parser*) dan pustaka validasi string dari potensi kegagalan memori (*runtime crash*).

Secara garis besar, strategi pengujian API dibagi menjadi tiga tingkat:

  • Pengujian Fungsional (Black-Box): Memvalidasi alur masukan dan luaran HTTP API pada berbagai *endpoint* seperti autentikasi akun (*login/logout*), kelola data siswa, pencatatan presensi, dan pemeriksaan kesehatan (*health check*).
  • Pengujian Unit & Integrasi (White-Box): Menguji efektivitas kerja perangkat lunak penengah (*middleware*) seperti otorisasi akses (*RBAC*), keamanan header (*security headers*), penanganan pembatasan laju (*rate limiting*), serta pencegahan injeksi data berbahaya.
  • Pengujian Invarian (Fuzz Testing): Menjamin ketahanan parser JWT dan utilitas sanitasi data agar tidak pernah menyebabkan kegagalan fatal pada proses peladen (*panic / crash*) ketika menerima data tidak terstruktur.

4.2. Kasus Uji (Test Cases)

Bagian ini mendokumentasikan rincian rancangan kasus uji yang diterapkan pada Absen Sholat API.

4.2.1. Pengujian Kotak Hitam (Black-Box Testing)

Pengujian kotak hitam berfokus pada ketepatan keluaran status HTTP dan skema respons JSON dari *endpoint* API berdasarkan masukan parameter permintaan.

Tabel 4.1. Skenario Kasus Uji Black-Box API & Endpoint

ID Tes Rute/Endpoint API Skenario Pengujian Masukan (Input) Hasil yang Diharapkan
BB-API-01 GET /health Verifikasi ketersediaan dan status sistem peladen secara berkala. Kirim permintaan GET ke /health. Status 200 OK dengan JSON respons {"status":"ok", "timestamp": ...}.
BB-API-02 POST /api/v2/auth/sessions Verifikasi penolakan autentikasi jika kata sandi salah. Payload JSON dengan NIS "12345" dan kata sandi yang salah. Status 401 Unauthorized dengan notifikasi kesalahan kata sandi.
BB-API-03 POST /api/v2/auth/sessions Verifikasi keberhasilan masuk akun dan perolehan token akses. Payload JSON dengan NIS "12345" dan kata sandi yang benar. Status 200 OK berisi string token JWT dan profil data pengguna.
BB-API-04 GET /api/v2/students Verifikasi pembatasan hak akses berbasis peran (RBAC). GET ke /students dengan token JWT bertipe peran "siswa". Status 403 Forbidden karena rute ini memerlukan hak akses "admin".
BB-API-05 POST /api/v2/auth/logout Verifikasi penonaktifan token JWT saat sesi berakhir. Kirim permintaan POST dengan menyertakan token JWT aktif di header. Status 200 OK, token JWT dimasukkan ke daftar cekal (*blacklist*) database.

4.2.2. Pengujian Kotak Putih (White-Box Testing)

Pengujian kotak putih memvalidasi logika internal pengolah rute (*router*), penyaringan middleware, serta validasi data masukan dari serangan eksploitasi web.

Tabel 4.2. Skenario Kasus Uji White-Box Middleware & Security

ID Tes Middleware / Fungsi Skenario Pengujian Kondisi Internal Kriteria Keberhasilan
WB-API-01 Security Headers Pemeriksaan kepatuhan header keamanan pada setiap respons HTTP. Rute API dipanggil oleh klien. Menyertakan header X-Content-Type-Options: nosniff dan X-Frame-Options: DENY.
WB-API-02 Rate Limiter Pencegahan serangan brute-force dan pemboman trafik API. Pengiriman > 6 request dalam 1 menit ke endpoint login. Klien diblokir dengan respons HTTP 429 Too Many Requests.
WB-API-03 Input Sanitizer Verifikasi ketahanan database terhadap serangan SQL Injection. Query parameter pencarian berisi string "1 OR 1=1". Middleware menangkap karakter berbahaya dan membalas dengan 400 Bad Request.
WB-API-04 Body Size Limiter Pencegahan serangan Denial of Service (DoS) melalui unggahan berkas raksasa. Payload berukuran lebih dari 10 megabyte dikirim ke server. Permintaan ditolak seketika dengan status 413 Payload Too Large.

4.2.3. Pengujian Invarian (Fuzz Testing / Property-Based)

Pendekatan pengujian invarian menggunakan metode pembangkitan input acak otomatis (fuzzing) untuk memastikan fungsi-fungsi pemroses string tidak memicu kesalahan runtime memori (*panic*).

Tabel 4.3. Skenario Uji Invarian / Fuzzing API

ID Tes Target Invarian Aturan Pengujian (Property) Metode Generator (Go Fuzzing)
PB-API-01 JWT Token Parser Safety Fungsi penelaah token JWT tidak boleh memicu *nil pointer dereference* atau *panic* akibat format string token acak atau rusak. Metode `go test -fuzz` menyuplai ribuan kombinasi byte string acak ke ParseToken().
PB-API-02 Validation Regexp Bounds Logika ekspresi reguler pada validator email dan sandi tidak boleh memicu *CPU exhaustion* (*Catastrophic Backtracking*). Membangkitkan string acak dengan panjang hingga 10.000 karakter ke fungsi validasi email.

Pengujian backend dijalankan menggunakan perangkat `go test` dengan hasil verifikasi seluruh modul menunjukkan tingkat kelulusan mutlak.
